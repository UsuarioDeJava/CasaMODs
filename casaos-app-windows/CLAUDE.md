# App Windows for CasaOS

A CasaMOD mod: CasaOS's apps open in windows inside the CasaOS tab (an iframe each, with a bar: icon, title, ⋯, new tab, minimize, maximize/restore, close), dragged, resized, minimized without stopping; Files and the App Store (CasaOS's Buefy modals) become windows too. See `README.md`.

- `app-windows/` is the mod as installed (`mod.js`, `mod.css`, `mod.json`, `preview.png`, and `frame-proxy.sh`, which the mod doesn't load: it ships there so the user runs it from the server's copy): no build step, copied as is to `/DATA/AppData/casamod/mod/app-windows/`.
- It is its own project and depends on no other mod. It tells others that a window is in use with `html.cw-active` (Idle Hide reads it).
- The CasaOS facts (README, "How it works") come from CasaOS-UI's source: `mixins/app/Business_OpenThirdApp.js` (`window.open`, the `#/launch?appDetailData=` page), `components/Apps/AppCard.vue` (`#app-<name>` cards, `.cards-content` icon, the `.app-card-drop` menu), `views/Home.vue` (Files: `b-modal` `.file-panel`, `destroy-on-hide=false`, v-show), `components/Apps/AppSection.vue` (App Store: `$buefy.modal.open`, `.app-panel`), `.top-bar`, `.close-button`.
- `app-windows/frame-proxy.sh` (run once on the server by the user, `sudo bash /DATA/AppData/casamod/mod/app-windows/frame-proxy.sh`): `tailscale serve` per Docker port → Caddy on `127.0.0.1:P+30000` (container `frame-proxy`, host network) → the app, without `X-Frame-Options` and CSP `frame-ancestors`. Its sites are `http://:Q` with `bind 127.0.0.1`: tailscale serve passes the browser's Host (`<machine>.<tailnet>.ts.net:P`), and an address like `http://127.0.0.1:Q` would add a Host matcher, so Caddy answered an empty 200 (blank pages). It drops `X-Forwarded-For` toward the apps (Home Assistant answers 400 to an untrusted proxy; the value would only be 127.0.0.1) and finds HTTPS apps by trying TLS on each port (curl), so a remapped port (MineOS on 8444) isn't proxied as plain HTTP (an empty 502, a blank window); `handle_errors` shows a message instead. It also writes App Windows' window page (`$DIR/www`: `frame.html`, `frame.js`, `ok.svg`), served on every app's address at `/__casaos-windows/` (`handle_path`, the rest in `handle`). The mod uses it when `ok.svg` loads; on the app's origin it catches F5 in the app (reloads the app) and posts the app's place and what it plays (Media Session + the media element) to CasaOS, which the mod turns into `casamods:nowplaying` (Live Wallpapers reads it, unchanged). Its sound: `captureStream()` of the playing element into an analyser set like Live Wallpapers' (fftSize 4096, smoothing 0.55, -85/-25 dB, 64 log bands 30 Hz–16 kHz, loudest bin 0–255), posted about 30 times a second only while `casamods:audio-wanted` is on (the mod relays it) and the app plays; the mod sends `casamods:audio` and Live Wallpapers mixes it in by the loudest. Keep the two band definitions the same. Checked in Chromium through the whole chain (front TLS Caddy as tailscale serve → caddy:2-alpine → a fake app with an audio element outside the DOM). Tested against the real images (caddy:2-alpine 2.11, homeassistant/home-assistant on host network, hexparrot/mineos on 8444:8443) with the headers tailscale serve sends; the Caddyfile also validates on Caddy 2.8.
- Caddy runs as the CasaOS app "Frame Proxy": the script writes `$DIR/docker-compose.yml` (fixed services plus `x-casaos`: title, icon `frame-proxy-icon.png` through jsDelivr, `port_map` = the page's port) and runs `docker compose -p frame-proxy … up -d`. CasaOS-AppManagement lists every Compose project on the host (`ComposeService.List`: the compose API's project list, loaded from each project's config file); a plain `docker run` container shows under "Legacy app (To be rebuilt)" (`app_type: container`). Without `docker compose` it falls back to `docker run`. Its card opens the Frame Proxy page (`$DIR/page`, Caddy's `http://:PAGE_PORT` site, 8390 by default, also served through `tailscale serve` like an app; without a page, CasaOS would open `http://<host>/` for the card). The page reads `state.json` (written last in each run) and adds or removes ports: its `/api/` POSTs (marked `X-Frame-Proxy: 1`, so another site can't send them) go on only from `remote_ip 127.0.0.1`, which is how tailscale serve's requests arrive (on the LAN the page is read-only), to `unix//srv/api/sock`: `frame-proxy-api.socket` (systemd, `Accept=yes`) runs `frame-proxy.sh api` per connection, which parses the request (digits and dots only), saves `$DIR/config` (`EXTRA`, `HTTPS_APPS`, `SKIP`, `PAGE_PORT`; the environment wins when given), answers, then starts a run with `systemd-run` (runs wait on `flock $DIR/lock`). `frame-proxy-scan.timer` runs `frame-proxy.sh scan` every minute: a new run only when `app_ports` differs from `$DIR/scanned`. Ports served last time and not now lose their `tailscale serve` line (`$DIR/served`). The script copies itself to `$DIR/frame-proxy.sh`, which the units run. `frame-proxy.sh window-page <folder>` writes only the window page (no root, Tailscale or Docker needed), for CasaOS on the user's own domain: the README's "CasaOS on your own domain" covers that case (each app a subdomain with its own https address in the user's proxy, its CasaOS Web UI set to it — App Windows keeps https addresses as they are and only moves http ones to CasaOS's host — and the frame headers removed there; Caddy's example validated with `caddy validate`). Checked with Docker Compose, a stub `tailscale`, a stand-in for the systemd socket and `systemd-run`, and the page in Chromium (remove, add with https, add back, scan; read-only from the LAN; `scan` with a new app and with none; `off`). Installing it automatically from the mod (a privileged helper app, installed through CasaOS's API, running the script as root on the host) is not built: it would let a page script run root commands on the server.
- Rules: a window's element never moves in the DOM once added (an iframe that moves reloads): order is z-index only (21–29, over CasaOS's `.top-bar`, which is 20). Windows use the whole tab (`area()` is the viewport): maximized covers the top bar, as the user asked. No per-frame work: a MutationObserver on `childList` plus the panels' own `style`, pointer events only while dragging.

## Working here

- The user is Brazilian: reply in Portuguese (pt-BR). Code, comments and README stay in English.
- Texts live in the `TEXT` table of `mod.js`, in all 31 CasaOS languages (`pt-pt` only overrides `pt`). A new or changed text needs every language — `node tests/text-check.js` fails otherwise.
- Tests: `node tests/text-check.js` (a second) and `node --check app-windows/mod.js`. There is no browser suite yet: the user tests on their CasaOS and doesn't want long test runs from here.
- Write files with LF line endings (Python on Windows: `open(..., 'w', newline='\n')`). Don't create `.html` files with the editor tool here: the desktop app opens them in the user's browser pane.
- The user's PC is low-end: keep it light.
- Bump `version` in `app-windows/mod.json` when the mod changes. At the end, tell the user what to copy: `app-windows/` to `/DATA/AppData/casamod/mod/` on the CasaOS server, then restart CasaMOD and reload with Ctrl+F5.
